# 프로젝트 헌장 (Project Charter)

- **문서 버전**: v1
- **작성일**: 2026-09-14
- **상태**: 확정

## 1. 배경

디지털데일리 「클라우드 시대 역설…24시간 GPU 돌리자니 다시 '소유'가 답?」 (2026-07-11) 는
기업들이 GPU 인프라 조달에서 딜레마에 빠져 있음을 보도했다.

기사에서 확인된 논지:

- GPU를 **24시간 상시 가동**하는 그룹에서 온프레미스 선호(101명)가 GPUaaS 선호(25명)의 **약 4배**
- 상시 사용 기업에게는 종량제가 오히려 "비용 폭탄"
- 24/365 풀 가동 기준 **약 1년 반**이면 구매 비용을 초과
- 하루 몇 시간 실험 위주는 클라우드, 풀 가동은 자체 구매가 경제적

> ⚠️ 위 수치는 검색 스니펫을 통해 확인한 것으로, 원문 전문(全文) 대조는 하지 못했다.
> 프로젝트 결과물에 기사 수치를 직접 인용할 경우 원문 재확인이 필요하다.
> 다만 **본 프로젝트의 문제 정의는 기사의 개별 수치가 아니라 논지 구조에 의존**하므로,
> 수치가 달라져도 프로젝트의 타당성은 변하지 않는다.

## 2. 문제 정의

기사가 제시한 판단 기준은 "사용 패턴"이다. 그런데 이 기준은 **실무에서 적용 불가능**하다.

| 기사의 전제 | 현실 |
|---|---|
| 조직은 자기 GPU 사용 패턴을 안다 | 할당량(request)만 알고 실사용량(usage)은 측정하지 않는다 |
| 사용 패턴은 안정적이다 | 워크로드마다 다르고 시간에 따라 변한다 |
| 비용은 조직 단위로 결정한다 | 학습과 추론의 경제성은 정반대다 |

**→ 핵심 문제: 조달 의사결정에 필요한 사용 패턴 데이터가 측정·집계·예측되지 않는다.**

## 3. 프로젝트 목표

> 실사용 GPU 트레이스로부터 수요를 집계·예측하고,
> 온디맨드 / 스팟 / 예약 / 소유의 TCO 손익분기를 산출하는
> **재현 가능한 데이터 파이프라인**을 구축한다.

### 3.1 최종 산출 지표

```
손익분기 가동률  U* = 연간 온프레미스 TCO / (온디맨드 시간단가 × 8,760 × GPU 수)
```

실측 가동률이 `U*`를 넘으면 소유가, 넘지 않으면 임대가 유리하다.
워크로드 유형별로 이 값을 각각 산출하는 것이 본 프로젝트의 차별점이다.

### 3.2 기대 결론 (가설)

| 워크로드 | 가동률 특성 | 예상 권장안 |
|---|---|---|
| 학습 / 배치 | 간헐적, 중단 허용 | 스팟 · 온디맨드 |
| 추론 서빙 | 상시, 중단 불가 | 예약 · 소유 |

**이는 가설이며, 데이터로 검증하거나 반증하는 것이 프로젝트의 일이다.**
반증되더라도 프로젝트는 성공이다 — 검증 가능한 결론을 냈기 때문이다.

## 4. 범위 (Scope)

### 4.1 포함

| 계층 | 내용 |
|---|---|
| **L1 진단** | 트레이스 수집 → 정제 → 차원모델링 → 팀/잡별 showback, 낭비 비용 정량화 |
| **L2 예측** | GPU-hour · 토큰 수요의 분위수(P50/P90) 예측, 백테스트 |
| **L3 처방** | TCO 시뮬레이터, 손익분기 곡선, 조달 믹스, 민감도 분석 |
| **부가** | 실시간 예산 소진율 알람 (스트리밍), 데이터 품질 게이트 |

### 4.2 제외 (명시적 비목표)

| 제외 항목 | 이유 |
|---|---|
| 커스텀 GPU 스케줄러 구현 | 연구 주제이며 데이터 엔지니어링 역량과 무관 |
| Kubernetes 클러스터 직접 구축 | 시간 대비 회수율이 낮고 본 문제와 무관 |
| 모델 파인튜닝 · LLM 학습 | 직무(데이터 엔지니어) 불일치 |
| 실시간 GPU 스케줄링 개입 | 본 프로젝트는 **분석·제안**까지이며 제어는 하지 않는다 |
| 대시보드 시각 디자인 고도화 | 기능 전달에 필요한 수준까지만 |

## 5. 성공 기준

프로젝트는 아래를 **전부** 만족할 때 완료로 간주한다.

### 5.1 필수 (L1)

- [ ] `docker compose up` 단일 명령으로 전체 파이프라인이 재현된다
- [ ] Airflow DAG가 **멱등(idempotent)** 하며 임의 구간 백필이 가능하다
- [ ] dbt 테스트가 전부 통과하고, 실패 시 파이프라인이 중단된다
- [ ] 요청 대비 실사용 갭(낭비)이 금액으로 산출된다
- [ ] 팀/워크로드 단위 showback 리포트가 생성된다

### 5.2 필수 (L2 / L3)

- [ ] 수요 예측이 **베이스라인(seasonal naive) 대비 성능이 문서화**되어 있다
      (이기지 못했다면 그 사실과 판단 근거가 기록되어 있을 것)
- [ ] 손익분기 가동률 `U*` 가 워크로드 유형별로 산출된다
- [ ] TCO 가정값에 대한 민감도 분석이 제공된다

### 5.3 필수 (문서)

- [ ] 모든 기술 선택에 ADR이 존재하며, **채택하지 않은 대안과 트레이드오프**를 포함한다
- [ ] 데이터의 알려진 한계가 README와 데이터 소스 문서에 명시되어 있다
- [ ] 파이프라인 처리량 · 백필 소요시간 등 벤치마크 수치가 기록되어 있다

### 5.4 안 되는 것 (실패 조건)

- 가격 데이터를 임의로 지어내는 것
- 베이스라인 없이 머신러닝을 채택하는 것
- 한계를 숨기고 정밀해 보이게 만드는 것

## 6. 제약과 가정

| 항목 | 내용 |
|---|---|
| 예산 | 0원. 전부 로컬 Docker 환경 (ADR-0003) |
| 기간 | 8주 (`docs/03-roadmap.md`) |
| 인력 | 1인 |
| 데이터 신선도 | 트레이스는 과거 데이터이며 실시간 수집이 아니다 (리플레이로 대체) |
| 가격 신선도 | AWS API에서 수집하되, 수집 시점이 트레이스 시점과 다르다 (ADR-0004) |

## 7. 주요 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 트레이스와 가격 데이터의 **시점 불일치** | 비용 절대값의 신뢰도 하락 | 절대값이 아닌 **상대 비교와 손익분기점**을 산출물로 정의. 모든 가정을 설정 파일로 노출하고 민감도 분석 제공 |
| 2개월 트레이스로 **계절성 학습 부족** | 예측 성능 한계 | 주간(weekly) 주기까지만 모델링 대상으로 한정하고 이를 명시 |
| Azure 추론 트레이스 스키마가 예상과 다름 | L1 추론 축 지연 | Week 1에 스키마 실측 검증을 완료. 불일치 시 알리바바 단독으로 축소하고 ADR-0002 개정 |
| 범위 확대로 인한 미완성 | 프로젝트 전체 실패 | **Week 4에 L1을 배포 가능 상태로 1차 완결.** 이후는 증분 |

## 8. 이해관계자

| 역할 | 대상 | 관심사 |
|---|---|---|
| 제작자 | 본인 | 데이터 엔지니어링 역량 증명 |
| 1차 독자 | 채용 담당자 · 기술 면접관 | 설계 근거, 재현성, 문제 해결 과정 |
| 가상 사용자 | 인프라 운영팀 / CTO | "빌릴까 살까"에 대한 실행 가능한 답 |

1차 독자가 실제 평가자이므로, **결정의 근거를 남기는 것**이 코드 자체만큼 중요하다.
이것이 ADR을 강제하는 이유다 (ADR-0000).
