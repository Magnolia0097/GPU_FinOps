# ADR-0007: 미완료(censored) 인스턴스를 집계에서 제외한다

- **상태**: 채택
- **일자**: 2026-09-15

## 배경

`pai_instance_table` 의 **30.15%** 가 `end_time IS NULL` 이다.
관측 창이 닫히는 시점에 아직 실행 중이던 인스턴스들이다 (우측 절단, right-censoring).

GPU-시간을 계산하려면 duration이 필요한데, 이들은 종료 시각을 모른다.
결측 규모가 30%이므로 처리 방식이 결론을 바꾼다.

## 결정

**미완료 인스턴스를 집계에서 제외한다.**

```sql
WHERE end_time IS NOT NULL AND end_time > start_time
```

제외된 비중과 그로 인한 편향 방향을 모든 리포트에 함께 표기한다.

## 근거

표준적인 우측 절단 처리는 "관측 종료 시점으로 절단"이다.
이를 먼저 적용했고, **물리적으로 불가능한 결과**가 나왔다.

```sql
-- 방식 A (기각)
coalesce(end_time, (SELECT max(end_time) FROM pai_instance_table)) - start_time
```

### 검산

```
클러스터 총 GPU        = 6,742장   (pai_machine_spec 합계)
관측 기간              = 68.94일 = 1,654시간
물리적 할당 상한       = 6,742 × 1,654 ≈ 11,151,000 GPU-hour
```

| 방식 | 할당 GPU-시간 | 상한 대비 | 낭비율 | 판정 |
|---|---|---|---|---|
| A. 관측종료로 절단 | 148,724,117 | **1,333%** | 94.96% | ❌ 불가능 |
| B. 미완료 제외 | 2,266,602 | 20.3% | **62.81%** | ✅ 타당 |

방식 A는 **존재하지 않는 GPU를 13배 할당**한 결과다.

### 왜 A가 틀렸는가

절단 자체가 틀린 게 아니라, 절단에 깔린 가정이 이 데이터에 맞지 않는다.

"관측 종료 시점으로 절단"은 **해당 작업이 관측 종료까지 계속 실행되었다**고 가정한다.
그런데 `end_time` 이 비어 있는 이유는 두 가지가 섞여 있다.

1. 정말로 관측 종료 시점까지 실행 중이었다 → 가정이 맞음
2. 트레이스 수집 과정에서 종료 이벤트가 유실되었다 → 가정이 틀림

2번이 섞여 있으면 관측 초반에 시작된 인스턴스일수록 duration이 과대 계상된다.
`plan_gpu` 가 큰 분산 학습 작업 하나가 수만 GPU-hour를 혼자 만들어낸다.
**`start_time` 이 이를수록 왜곡이 커지는 구조적 편향**이다.

### B의 편향은 방어 가능하다

방식 B는 장기 실행 작업을 체계적으로 빠뜨린다.
장기 작업은 일반적으로 가동률이 높으므로, **낭비율을 과소 추정**하는 방향이다.

즉 62.81%는 **보수적 하한**이다.
"실제 낭비는 이보다 클 수 있다"는 진술은 안전하지만,
방식 A의 94.96%는 물리적으로 불가능한 수치라 어떤 방향으로도 방어할 수 없다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|---|---|---|---|
| A. 관측 종료로 절단 | 표준 기법, 데이터 손실 없음 | 물리적 상한의 13배 산출 | **검산 실패** |
| C. 완료 인스턴스의 duration 분포로 대체 | 데이터 손실 없음 | 미완료가 무작위 표본이 아님(길수록 미완료 가능성↑) → 오히려 과소 대체 | 대체값의 근거가 약함 |
| D. 생존분석(Kaplan-Meier)으로 기대 duration 추정 | 통계적으로 정교 | 8주 예산 초과. 종료 이벤트 유실과 진짜 절단을 구분할 수 없어 전제가 무너짐 | 정교함이 전제의 오류를 고치지 못함 |
| E. 태스크의 `end_time` 으로 인스턴스 보간 | 상위 레코드 활용 | 태스크도 27.72% 결측. 근본 해결 아님 | 결측이 상관되어 있음 |

## 결과

**얻는 것**
- 물리적으로 타당한 집계
- 편향 방향이 한쪽으로 명확 (과소 추정) → 서술로 방어 가능

**포기하는 것**
- 인스턴스의 30.15% (GPU-시간 기준으로는 더 큰 비중일 수 있음)
- 장기 실행 워크로드에 대한 대표성

**강제 규칙**
1. 모든 낭비 리포트에 **제외 비율을 함께 표기**한다.
2. 리포트 문구는 "낭비율 62.8%" 가 아니라
   **"완료된 인스턴스 기준 낭비율 62.8% (인스턴스의 30.2% 제외, 과소 추정 방향)"** 로 쓴다.
3. 모든 GPU-시간 집계에 **물리적 상한 대조를 dbt 테스트로 강제**한다.
   `allocated_gpu_hours <= total_gpus × elapsed_hours × 1.05` 를 넘으면 파이프라인을 실패시킨다.

3번이 이 사건의 실질적 교훈이다. 이 버그는 낭비율만 봐서는 드러나지 않았고,
절대량을 물리적 상한과 대조했을 때만 잡혔다.

## 재검토 조건

- 트레이스 배포처가 종료 이벤트 유실 여부를 공식 문서화하면 재검토한다.
- 방식 B의 제외 비중이 GPU-시간 기준 50%를 넘는 세부 그룹이 나오면
  해당 그룹은 리포트에서 별도 표기하거나 제외한다.
