# 아키텍처 결정 기록 (ADR)

## 왜 ADR인가

코드는 **무엇을** 했는지 보여주지만 **왜** 그렇게 했는지는 보여주지 않는다.
포트폴리오의 1차 독자는 기술 면접관이고, 그들이 알고 싶은 것은 후자다.

특히 AI 도구를 사용해 작성한 코드라면 더욱 그렇다.
AI는 코드를 대신 써 줄 수 있지만 **트레이드오프 판단을 대신 해 주지는 않는다.**
ADR은 그 판단이 실제로 있었다는 증거다.

## 작성 규칙

1. 한 결정당 한 파일. 번호는 순차 부여.
2. **채택하지 않은 대안과 그 이유를 반드시 포함한다.** 이 항목이 없는 ADR은 ADR이 아니다.
3. 결정이 번복되면 기존 문서를 수정하지 않고 `상태: 대체됨 (→ NNNN)` 으로 표시한 뒤 새 ADR을 쓴다.
   **번복 이력 자체가 가치 있는 기록이다.**

## 템플릿

```markdown
# ADR-NNNN: 제목

- 상태: 제안 | 채택 | 대체됨 (→ NNNN) | 폐기
- 일자: YYYY-MM-DD

## 배경
어떤 상황에서 무엇을 결정해야 했는가.

## 결정
무엇을 하기로 했는가.

## 근거
왜 그렇게 했는가.

## 검토한 대안
| 대안 | 장점 | 단점 | 기각 사유 |

## 결과
이 결정으로 무엇을 얻고 무엇을 포기하는가.

## 재검토 조건
어떤 상황이 되면 이 결정을 다시 봐야 하는가.
```
