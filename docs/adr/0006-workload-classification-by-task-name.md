# ADR-0006: 워크로드 분류를 `task_name` 기반으로 재정의한다

- **상태**: 채택
- **일자**: 2026-09-15
- **관련**: ADR-0002 의 워크로드 축 부분을 대체

## 배경

ADR-0002는 두 축을 전제했다.

1. Alibaba 트레이스의 `pai_group_tag_table.workload` 로 워크로드 유형 분류
2. Azure LLM Inference 트레이스로 추론 서빙 축 확보

Week 1 실측에서 **둘 다 성립하지 않았다.**

### 문제 1 — Azure 트레이스 접근 불가

개발 환경의 egress 정책이 Azure Blob Storage 호스트를 차단했다 (`docs/failures.md`).
재시도로 우회할 수 있는 종류가 아니다.

### 문제 2 — `workload` 컬럼이 비어 있고, 채워져 있어도 쓸 수 없다

| 항목 | 실측값 |
|---|---|
| `workload` 채움률 | **9.74%** (1,055,032행 중 102,798행) |
| `gpu_type_spec` 채움률 | 1.96% |
| 값의 성격 | `bert`, `ctr`, `nmt`, `inception`, `graphlearn`, `resnet`, `xlnet`, `rl`, `vgg` |

채움률도 문제지만 더 근본적인 문제는 **값이 모델 이름이라는 것**이다.
`bert` 가 학습 중인지 추론 서빙 중인지 이 컬럼은 말해주지 않는다.
ADR-0002가 원했던 "학습 vs 추론" 구분에 애초에 쓸 수 없는 컬럼이었다.

## 결정

`pai_task_table.task_name` 을 워크로드 분류의 1차 축으로 사용한다.
채움률 100%이며, 값이 **역할(role)** 을 나타낸다.

| task_name | 비중 | 분류 |
|---|---|---|
| `tensorflow` | 49.28% | 단일 프로세스 학습 |
| `worker` | 21.87% | 분산 학습 워커 |
| `ps` | 14.53% | 분산 학습 파라미터 서버 |
| `PyTorchWorker` | 8.79% | 분산 학습 워커 |
| `xComputeWorker` | 2.17% | 연산 워커 |
| `evaluator` | 1.36% | 평가 |
| `TensorboardTask` | 0.85% | 보조 (비연산) |
| `JupyterTask` | 0.16% | 대화형 |

여기에 `inst_num`(태스크당 인스턴스 수, 76%가 1)을 결합해 아래 축을 만든다.

```
distributed_training : ps/worker/PyTorchWorker 조합, inst_num > 1
single_training      : tensorflow 단독, inst_num = 1
interactive          : JupyterTask (사람이 붙어 있는 대화형)
auxiliary            : TensorboardTask, evaluator 등 비연산 보조
```

**추론 서빙 축은 이 데이터에 존재하지 않는다고 명시한다.**
없는 것을 있는 척 만들지 않는다.

## 근거

1. **`task_name` 은 비용 의사결정과 직접 연결된다.**
   `workload` 의 모델명(`bert`)은 "그래서 어쩌라고"로 끝나지만,
   역할은 실행 가능한 결론으로 이어진다. 실제 측정 결과:

   | 역할 | 할당 GPU-시간 | 낭비율 |
   |---|---|---|
   | `ps` | 239 | **99.2%** |
   | `JupyterTask` | 1,489 | **96.1%** |
   | `OpenmpiWorker` | 11,851 | 99.3% |
   | `tensorflow` | 294,036 | 77.0% |
   | `worker` | 1,408,198 | 67.8% |
   | `PyTorchWorker` | 546,644 | **41.7%** |

   → "파라미터 서버에 GPU를 할당하지 마라", "유휴 노트북을 자동 종료하라" 는
   구체적 권고가 나온다. 이것이 FinOps 산출물의 올바른 형태다.

2. **채움률 100%라 커버리지 편향이 없다.**
   9.74%짜리 컬럼으로 낸 결론은 나머지 90%에 대해 아무것도 말하지 못한다.

3. **분산 학습 여부는 조달 전략과 직결된다.**
   분산 학습은 여러 인스턴스가 동시에 살아 있어야 하므로 스팟 중단에 취약하다.
   단일 인스턴스 작업은 중단되어도 재시작 비용이 작다.
   → 스팟 배정 가능 여부를 가르는 실질적 기준이다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 사유 |
|---|---|---|---|
| `workload` 컬럼을 채워진 9.74%에만 적용 | 원 설계 유지 | 90%에 대해 말할 수 없고, 채워진 행이 무작위 표본이라는 근거도 없음 | 커버리지 편향이 결론을 무의미하게 만듦 |
| 추론 워크로드를 합성해 추가 | 축이 살아남 | 합성 데이터로 결론을 내는 것 | **ADR-0002가 명시적으로 금지**. 치명적 |
| 작업 길이로 학습/추론 추정 | 데이터만으로 가능 | 짧은 작업 = 추론이라는 근거가 없음. 실패한 학습도 짧다 | 검증 불가능한 가정 |
| Azure 데이터를 사용자 로컬에서 받아 반입 | 원 설계 유지 | 개발 루프가 끊기고 재현성이 깨짐 | 지금 진행 불가. 단 **후속 확장 경로로는 열어둔다** |
| 다른 공개 추론 트레이스 탐색 | 축 확보 가능 | Week 1 일정 초과, 접근성 재차 불확실 | 현 단계에서 범위 초과 |

## 결과

**얻는 것**
- 채움률 100%의 분류 축
- 역할 단위의 실행 가능한 권고 (PS·노트북 낭비)
- 스팟 배정 가능성 판단의 실질적 근거 (분산 여부)

**포기하는 것**
- **추론 서빙 축.** 이 프로젝트는 학습/배치 워크로드만 다룬다.
- 따라서 원 기사의 "24시간 상시 가동" 논점에 **직접 답할 수 없다.**
  대신 "간헐적 학습 워크로드에서 소유 vs 임대"라는 축소된 질문에 답한다.

**서사 변경**

README와 프로젝트 헌장의 결론 구조를 아래로 수정한다.

| 기존 (ADR-0002) | 변경 후 |
|---|---|
| 학습은 스팟, 추론은 소유 | 학습 워크로드 내부에서도 역할별로 경제성이 갈린다 |
| 두 트레이스 병렬 비교 | 단일 트레이스, 역할 축으로 분해 |

**이 변경은 프로젝트를 약화시키지 않는다.** 오히려 "데이터가 없으면 결론을 내지 않는다"는
원칙을 지킨 기록이 남는다. 기사 논점 전체를 다루지 못한다는 한계는 README에 명시한다.

## 재검토 조건

- Azure 트레이스 접근이 가능해지면 추론 축을 **추가**한다. 기존 축은 그대로 둔다.
- `task_name` 기반 분류가 실제 낭비 패턴을 설명하지 못하면
  (역할 간 낭비율 차이가 유의하지 않으면) 분류 축 자체를 재검토한다.
  → Week 1 실측에서 41.7%~99.3%의 뚜렷한 차이를 확인했으므로 현재는 유효하다.
