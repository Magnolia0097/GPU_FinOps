# 실패 · 시행착오 기록

> 순탄하게 완성된 프로젝트보다, 막히고 되돌아온 흔적이 있는 프로젝트가 신뢰를 얻는다.
> 이 문서는 부끄러운 기록이 아니라 **실제로 손을 댔다는 증거**다.

## 기록 규칙

1. 30분 이상 막힌 문제, 또는 결론을 바꾼 발견은 기록한다.
2. 결정을 번복했다면 ADR에 남기고, 구체적 증상은 여기에 남긴다.
3. 형식: 시도한 것 → 발생한 문제 → 해결 → 배운 것

### 2026-09-15 — 공식 데이터 배포처(OSS)가 egress 정책에 차단됨

**시도한 것**

`docs/02-data-sources.md` 에 적힌 공식 경로로 트레이스를 받으려 했다.

```
https://aliopentrace.oss-cn-beijing.aliyuncs.com/v2020GPUTraces/<table>.tar.gz
```

**발생한 문제**

```
curl: (56) CONNECT tunnel failed, response 403
```

개발 환경의 egress 정책이 해당 도메인을 허용하지 않았다. 재시도로는 해결되지 않는
정책 차단이었다.

**해결**

원본 README가 안내하는 GitHub 미러(`qzweng/clusterdata-cluster-trace-gpu-v2020-data`)로
전환했다. 미러는 GitHub 파일 크기 제한 때문에 tar.gz를 30MB 단위로 분할해두었으므로
`cat *.part* > file.tar.gz` 로 병합이 필요하다.

`scripts/fetch_data.sh` 를 **두 경로를 모두 지원**하도록 작성했다.
`SOURCE=auto` 가 기본값이고 OSS 실패 시 미러로 자동 전환한다.

미러 README에 sha256이 고시되어 있어 **7개 파일 전부 체크섬 검증 후 추출**했다.
경로가 바뀌어도 무결성은 보장된다.

**배운 것**

- 데이터 수집 스크립트에 경로가 하나뿐이면 그 경로가 막히는 순간 파이프라인 전체가 멈춘다.
  대체 경로와 체크섬 검증은 선택이 아니다.
- 미러를 쓸 때 체크섬이 없으면 "받긴 받았는데 같은 데이터인지 모르는" 상태가 된다.
  공식 배포처가 아닌 곳에서 받을수록 무결성 검증이 중요하다.

### 2026-09-15 — Azure 추론 트레이스도 차단, 워크로드 축 설계 변경

**시도한 것**

ADR-0002에 따라 Azure LLM Inference 트레이스로 추론 서빙 축을 만들려 했다.

**발생한 문제**

Azure Blob Storage 호스트 역시 egress 정책에 차단되어 있었다.

```
azurepublicdatasettraces.blob.core.windows.net      → 403
azurecloudpublicdataset2.blob.core.windows.net      → 403
```

**해결**

→ ADR-0006 참조. Alibaba 트레이스 내부에서 워크로드 축을 확보하는 쪽으로 설계를 바꿨다.

**배운 것**

데이터 소스를 확정하기 전에 **실제로 받아보는 절차**가 설계보다 먼저였어야 했다.
ADR-0002를 쓸 때 스키마 불일치는 리스크로 적었지만 "접근 자체가 막힐 가능성"은
고려하지 않았다. 접근성은 스키마보다 먼저 확인할 항목이다.

### 2026-09-15 — `group_tag.workload` 채움률이 9.74%였다

**시도한 것**

`pai_group_tag_table.workload` 로 학습/추론 워크로드를 분류할 계획이었다.
컬럼이 존재한다는 것은 헤더 파일로 확인했고, ADR-0002의 핵심 가정이었다.

**발생한 문제**

프로파일링 결과 두 가지가 동시에 틀렸다.

| 기대 | 실제 |
|---|---|
| 대부분의 행에 값이 있을 것 | **채움률 9.74%** (105만 행 중 10만) |
| 학습/추론 구분이 들어 있을 것 | **모델 이름만 들어 있음** |

실제 값 분포: `bert`(53%), `ctr`(26%), `nmt`(10%), `inception`, `graphlearn`,
`resnet`, `xlnet`, `rl`, `vgg`

즉 이 컬럼으로는 "무슨 모델인가"만 알 수 있고 "학습인가 추론인가"는 알 수 없다.
`gpu_type_spec` 은 더 심해서 채움률 1.96%였다.

**해결**

`pai_task_table.task_name` 이 대체재가 되었다. 채움률 100%이고 역할이 그대로 드러난다.

| task_name | 비중 | 의미 |
|---|---|---|
| tensorflow | 49.28% | 단일 프로세스 TF 작업 |
| worker | 21.87% | 분산 학습 워커 |
| ps | 14.53% | **파라미터 서버** |
| PyTorchWorker | 8.79% | 분산 PyTorch 워커 |
| evaluator | 1.36% | 평가 |
| JupyterTask | 0.16% | 대화형 노트북 |

`ps` + `worker` 조합의 존재는 **분산 학습**의 명확한 지표다.
→ ADR-0006으로 분류 체계를 재정의했다.

**배운 것**

- 컬럼이 **존재한다**는 것과 **채워져 있다**는 것은 완전히 다른 문제다.
  헤더만 보고 설계를 확정한 것이 실수였다.
- 스키마 검증에는 채움률(fill rate) 측정이 반드시 포함되어야 한다.
  `docs/01-metric-dictionary.md` 의 데이터 품질 지표에 이 항목을 추가했다.
- 결과적으로 더 나은 분류 축을 찾았다. `workload` 는 모델명이라 비용 의사결정과
  직접 연결되지 않지만, `task_name` 은 **역할**이라 "PS에 GPU를 주지 마라" 같은
  실행 가능한 결론으로 이어진다.

### 2026-09-15 — 미완료 인스턴스 절단 방식 때문에 할당량이 65배 부풀었다

**시도한 것**

`end_time IS NULL` 인 인스턴스(전체의 30.15%)를 어떻게 처리할지 정해야 했다.
교과서적인 우클리핑(right-censoring) 처리인 **"관측 종료 시점으로 절단"** 을 먼저 적용했다.

```sql
coalesce(end_time, (SELECT max(end_time) FROM pai_instance_table)) - start_time
```

**발생한 문제**

낭비율이 **94.96%** 로 나왔다. 너무 높아서 의심스러웠다.
할당 GPU-시간을 확인하니 **148,724,117 GPU-hour** 였다.

검산해보니 말이 안 되는 수치였다.

```
클러스터 총 GPU 수        ≈ 6,742장
관측 기간                 ≈ 68.94일 = 1,654시간
물리적 상한               ≈ 6,742 × 1,654 ≈ 11,151,000 GPU-hour

계산된 할당량 148,724,117 GPU-hour = 물리적 상한의 13.3배
```

**존재하지 않는 GPU를 할당한 셈**이므로 계산이 틀린 것이다.

원인: 관측 초반에 시작해 끝나지 않은 인스턴스에 **69일치 duration이 통째로 부여**된다.
`plan_gpu` 가 큰 분산 학습 작업 하나가 수만 GPU-hour를 혼자 만들어낸다.
`start_time` 이 이를수록 왜곡이 커지는 구조적 편향이다.

**해결**

미완료 인스턴스를 **제외**하는 방식(B)을 채택했다.

| 방식 | 할당 GPU-시간 | 낭비율 | 물리적 상한 대비 |
|---|---|---|---|
| A. 관측종료로 절단 | 148,724,117 | 94.96% | **1,333%** ❌ |
| B. 미완료 제외 | 2,266,602 | **62.81%** | 20.3% ✅ |

방식 B는 장기 실행 작업을 빠뜨리므로 **낭비율을 과소 추정**한다.
즉 62.81%는 보수적 하한이며, 이 방향의 편향은 명시하면 방어 가능하다.
반대로 방식 A는 과대 추정인데 그 크기가 물리적으로 불가능한 수준이었다.

→ ADR-0007로 결정을 기록했다.

**배운 것**

- **모든 집계에는 물리적 상한 검산이 붙어야 한다.** 이 버그는 낭비율(94.96%)만
  봐서는 "GPU를 많이 놀리는구나" 로 지나칠 수 있었다. 절대량을 상한과 대조했을 때만
  드러났다.
- 표준 통계 기법(우클리핑 절단)이 도메인에서는 틀릴 수 있다. 절단 자체는 옳지만
  "관측 종료까지 계속 실행되었다"는 암묵적 가정이 이 데이터에는 맞지 않았다.
- 결측 30%는 "조금 빠졌네" 수준이 아니라 **처리 방식이 결론을 바꾸는 규모**다.
