## Week 2–3 — L1 배치 파이프라인

| 작업 | 비고 |
|---|---|
| Docker Compose 환경 (MinIO · Postgres · Airflow) | |
| Bronze: 원본 적재 (수집 시각 · 소스 메타데이터 포함) | |
| Silver: 정제 · 표준화 · 타입 통일 | dbt |
| Gold: 차원 모델 | `fct_gpu_usage_hourly`, `fct_job_cost`, `dim_machine`, `dim_gpu_type`, `dim_workload`, `dim_price_point` |
| 가격 수집 DAG (AWS Price List · Spot History) | |
| dbt 테스트 · 데이터 품질 게이트 | |
| Airflow DAG **멱등성 · 백필** 구현 | |

**완료 기준**
- 임의 날짜 구간 백필이 동작하고 **재실행해도 결과가 동일**하다
- dbt 테스트 실패 시 DAG가 중단된다
- 파이프라인 처리량 · 백필 소요시간이 측정되어 기록되어 있다

> 이 구간이 **데이터 엔지니어 역량의 본체**다. 가장 많은 시간을 쓸 것.
> 멱등성과 백필이 동작하지 않으면 나머지가 아무리 화려해도 감점이다.

## Week 4 — L1 완결 · 1차 배포 🚩

| 작업 | 비고 |
|---|---|
| 비용 모델 (사용량 × 가격 조인) | |
| 낭비 지표 산출 (`gpu_waste_ratio`, `waste_cost_krw`) | |
| 팀 / 워크로드별 showback 리포트 | |
| 대시보드 (Streamlit 또는 Superset) | 기능 전달 수준까지만 |
| README 갱신 · 스크린샷 | |

**완료 기준 — 여기서 한 번 "완성"된다**
- `docker compose up` → 대시보드 접속까지 **타인이 재현 가능**
- 낭비가 **금액으로** 제시된다
- 이 시점의 저장소만으로도 포트폴리오로 제출 가능하다

## Week 5–6 — L2 예측

| 작업 | 비고 |
|---|---|
| 베이스라인 3종 구현 (`naive`, `seasonal_naive_168h`, `moving_average_24h`) | **먼저** |
| 백테스트 프레임워크 (rolling origin) | |

| 스팟 가격 예측 | 실측 시계열 |

- **이기지 못했다면 그 사실과 베이스라인 채택 결정이 기록되어 있다** (이것도 성공이다)
- P90 coverage가 측정되어 있다

## Week 7 — L3 처방 🚩

| 작업 | 비고 |
|---|---|
| 온프레미스 TCO 모델 (`config/tco.yaml` 기반) | |
| **손익분기 가동률 `U*` 산출** | 워크로드 유형별 |
| 손익분기 시점(`breakeven_months`) 곡선 | 기사의 "1년 반" 주장과 대조 |
| 조달 믹스 최적화 (P90 수요 기준) | |
| **민감도 분석** (전력단가 · 환율 · 감가상각 · 장비가) | |

**완료 기준**
- 기사의 질문에 **숫자로** 답하는 화면이 존재한다
- "가정이 ±30% 흔들리면 결론이 뒤집히는가"에 답할 수 있다
- 결론이 단일 숫자가 아니라 **범위**로 제시된다
